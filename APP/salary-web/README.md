# 工资核算网页版

把 `工资.xlsx` 改造为网页版：数据库后台 + 按年显示 + 个税次月计算。

## 快速开始

```bash
cd APP/salary-web           # 从仓库根目录进入
node src/server.js          # 默认 http://127.0.0.1:8788，用完 Ctrl+C
node --test test/           # 运行全部测试（30 项）
```

零第三方依赖：只用 Node 内置的 `node:sqlite` / `node:http`（需 Node ≥ 22，本机 v26）。

首次启动自动建库 `data/salary.db`（**零初始业务数据**，仅写入工资项字典），从 2026 年 1 月开始手工录入即可。

环境变量：`PORT`（端口）、`DB_FILE`（数据库路径，支持绝对路径与 `:memory:`）。

## 已实现的三条需求

### 需求 1：工资项暂定，结构支持后续调整

工资项存于字典表 `wage_item`，月度数据只存 `项ID + 金额`，**不写死在表结构里**。

| code | 名称 | 类别 | 带入 |
|---|---|---|---|
| post_salary | 职务 | 应发 | 是 |
| grade_salary | 级别 | 应发 | 是 |
| reserve_allowance | 保留补贴 | 应发 | 是 |
| living_allowance | 生活性补贴 | 应发 | 是 |
| work_allowance | 工作性津贴 | 应发 | 是 |
| base_perf | 基础绩效 | 应发 | 是 |
| fund | 公积金 | 代扣 | 是 |
| medical | 医保 | 代扣 | 是 |
| pension | 养老 | 代扣 | 是 |
| annuity | 年金 | 代扣 | 是 |

后期增删项：改 `src/config.js` 的 `WAGE_ITEMS`（`seedItems` 幂等 upsert）或直接写 `wage_item` 表，页面列随字典自动变化。本期按约定不做改名 UI。

### 需求 2：修改后自动带入下月，补发补扣不带入

- **触发时机**：保存草稿（方案 A）。
- **参与带入**：`carry_forward=1` 的常规项。
- **不带入**：补发（`makeup`）、补扣（`clawback`）—— 它们存在 `wage_adjustment` 表，与常规值物理隔离，"带入"只扫描 `wage_item_value`，**从结构上就不会误带**。
- **级联**：修改 M 月会逐月向下传播，直到遇到手工值 / 已确认月 / 记录不存在。
- **12 月 → 次年 1 月**：会带入（`CARRY_ACROSS_YEAR=true`）。
- **已确认月**：允许修改，但改动只在当前行生效，不向外传播。
- **未到达月份**：下月记录会生成，前端以 `future` 样式淡显并标注「未到达」。
- **下月已有手工值**：默认**不覆盖**（`CARRY_OVERWRITE_MANUAL=false`）—— 这是对第 7 条答复文本的落地选择，如需改为强制覆盖，改该常量即可。

页面表现：灰底输入框 = 带入值（悬停显示来自哪个月），白底 = 手工值。

**代扣与补扣分开**：代扣项基准值存 `wage_item_value`，补扣额存 `wage_adjustment`；计税时同类代扣合并（基准 + 补扣）一并进入本期专项扣除。这样补扣不会被固化成新基准。

### 需求 3：先用今年数据调试

- **次月计算上月**：`计税期 = 工资月 + 1`。某月工资行的个税 = 「计算月 == 该月」的计税期结果。
  已用工作簿验证：`工资核实 2026-01` 的个税 `29.36` 对应 `个税计算表 B=2026-01`（工资月 `2025-12`）。
- **年度累计按工资月归年**（口径 A，与现有电子版一致）：每个工资年 1 月累计从头开始。
  工作簿佐证：`个税计算表` 工资月 `2026-01` 行 `累计收入=11911`、`累计减除=5000`，是全新起点。
- **跨年衔接只写死结果**：`src/config.js` 的 `TAX_SEED_BY_TAX_PERIOD['2026-01'] = 29.36`。
  即 2026 年 1 月工资行的个税直接取该常数，不参与真实跨年累计，也**不污染** 2026 年度累计。
- **2026-12 工资月的个税不写死**：正常归入计税期 `2027-01` 计算。
- **专项附加定额**：按工资月年份配置（2025/2026 = 3000）；按约定今年无变化。

## 手动改写：所有自动计算结果都可改，且与计算值明显区分

任何由公式算出的结果都能直接改，改写值优先，**同时保留原自动计算值**，可一键还原。

**工资明细可改写字段**：应发合计、专项合计、个税、代扣合计、预计实发
**个税计算可改写字段**：工资收入、补计、专项扣除、其他扣除、累计收入、累计减除、专项累计、其他扣除累计、专项附加、应纳税额、一次性奖金、奖金税、累计税额、本期应缴、合计

**传播规则**（按依赖顺序，下游以上游最终值为准）：
```
应发合计 / 专项合计  →  计税期的工资收入 / 专项扣除
累计收入  →  应纳税额  →  累计税额  →  本期应缴  →  合计
```
若下游自己也有改写，则**下游改写优先**，不被上游传播覆盖（如锁定本期应缴后改累计收入，应缴仍取锁定值）。

**视觉区分**：

| 状态 | 样式 |
|---|---|
| 自动计算 | 淡蓝底 + 蓝色斜体数字 |
| 手动改写 | 琥珀底 + 加粗深褐数字 + 左侧橙色色条 + 右上角「改」标记 + ↺ 还原按钮 |

页面顶部有图例；有改写的月份在月份列显示「改写」标签。输入框清空或点 ↺ 即还原为自动计算。

**API**：
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/override/fields` | 可改写字段清单 |
| PUT | `/api/override/wage/:period` | 改写工资月字段 `{overrides:{gross:123}}`，传 `null` 还原 |
| PUT | `/api/override/tax/:taxPeriod` | 改写计税期字段 |
| POST | `/api/override/wage/:period/reset` | 还原该月全部改写 |
| POST | `/api/override/tax/:taxPeriod/reset` | 同上 |

数据存放在 `value_override` 表；`tax_period.autos` 保存各字段的自动计算值快照。

## 目录结构

```
salary-web/
  src/
    config.js     业务常量（工资项字典、税率表、带入开关、跨年写死值）
    period.js     期间工具（YYYY-MM 运算、次月计算、round2）
    db.js         schema + 初始化（node:sqlite）
    override.js   手动改写（可改字段清单、读写、auto/value 打包）
    tax.js        计税引擎（累计预扣 + 一次性奖金 + 改写传播）
    carry.js      带入引擎
    service.js    服务层（工资/带入/个税/银行卡/核对/改写）
    server.js     HTTP 服务 + 静态文件
  public/         前端（index.html / app.js / style.css）
  test/           测试（core.test.js 15 / override.test.js 13 / frontend.test.js 2）
  scripts/        extract.py（仅口径参考，不导入业务数据）
  data/           salary.db（运行时自动生成，已 .gitignore）
```

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/meta` | 工资项字典、银行类型、今天、写死期配置 |
| GET | `/api/wages/:year` | 某年 12 个月完整数据 |
| GET | `/api/wage/:period` | 单月详情 |
| PUT | `/api/wage/:period` | 保存单月（触发带入） |
| POST | `/api/wage/:period/confirm` | 确认/取消确认 |
| GET | `/api/tax/:year` | 某年计税期列表 |
| POST | `/api/recalc` | 全量重算 |
| GET/POST | `/api/bonus` | 一次性奖金（每年一笔） |
| GET/POST/PUT/DELETE | `/api/bank` | 银行卡流水 |
| GET | `/api/reconcile/:year` | 核对（预计 vs 实际） |
