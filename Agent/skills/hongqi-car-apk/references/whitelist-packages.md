# 白名单包名：取证、清单与占用矩阵

## 为什么必须"取证"而不是"编造"

红旗车机魔改了 PackageManager，维护一份**精确匹配**的包名白名单。
不在名单内的包名会被直接拒绝安装——也就是说，**改包名这个动作本身不创造安装资格**，
它只是把应用伪装成名单内的某个身份。因此新包名必须来自真实放行的条目。

这是最常见的失败原因：随意起一个 `com.xxx.yyy`，结果与没改一样被拒。

## 取证方法：解析"已经能装成功"的样本

最可靠的做法是拿任意一个**已确认能在该车机上安装成功**的 APK，
直接读出它的包名——那个包名就是白名单条目。

```bash
SK=<技能目录>
# 方式一：轻量侦查（不依赖 apktool，秒出）
python3 $SK/scripts/axml_meta.py 样本.apk --detect

# 方式二：只看包名与签名
python3 $SK/scripts/dump_manifest.py 样本.apk
```

`--detect` 会一并打印包名、MAIN/LAUNCHER Activity 与 `<application>` 级
meta-data，是排查时最常用的单条命令。

### 判读技巧：样本是不是"改包名"做出来的

- 若样本的 `resources.arsc` 与"未改包的原版"**文件大小完全相同**、只有 CRC 不同，
  说明样本也是靠"改包名"实现的——`ResTable_package.name` 是固定长度字段，
  原地改写不会改变文件长度。
- 若某几个样本之间**只在** `AndroidManifest.xml` / `resources.arsc` / 签名文件上不同，
  其余条目一致，则它们是同一个 app 的多份改包产物。
- 在 dex 中检索"新包名"若**出现次数为 0**，说明该应用的 manifest 包名
  与代码包名不同源，改包名对代码零影响（安全）。

## 红旗 H5 实测放行的三个包名

| 包名 | 车机占用情况 | 选用建议 |
|---|---|---|
| `com.android.gallery3d` | 一般为空 | **首选**：图库在车机精简系统中通常未预装 |
| `com.android.htmlviewer` | 一般为空 | 次选，常用于与 gallery3d 交替测试 |
| `com.android.statementservice` | 可能已被其他应用占用 | 不要用，装了会覆盖已有应用 |

三者都是 AOSP 系统应用包名。车机跑的是精简版 Android，这些 AOSP 应用通常
并未实际预装，所以包名"空着"，正好可用。若某个包名对应的系统应用**确实预装**了，
装同名包会因签名不同而报冲突——换另一个即可。

## 三条硬规则

1. **一个包名只能存在一个应用。** 分配新包名前必须确认它没被已有应用占用，
   否则新装的应用会**覆盖**掉占用者（若签名一致），或直接报签名冲突（若不一致）。
2. **签名必须与占用者一致。** 红旗车机的样本均用 AOSP testkey 签名（见 SKILL.md），
   因此用同一张 testkey 签名可获得"视为更新"的平滑覆盖。
3. **不要触碰用户正在使用的包名。** 交付前先确认目标包名是否被已有可用应用占用，
   并在交付说明里明确标注"哪些文件不要安装"。

## 包名分配的做法

给出多个候选包名时，用途是：
- 让多个第三方应用**共存**（各占一个）；
- 或做 **A/B 对照实验**（同一应用的两个变体轮流占用，测试某项配置的效果）。

参考交付形态：

| 文件 | 包名 | 用途 |
|---|---|---|
| 应用A-后台启动版 | com.android.gallery3d | 对照组（无桌面注册） |
| 应用A-桌面显示版 | com.android.gallery3d | 实验组（含桌面注册），可直接覆盖上一行 |
| 应用B-后台启动版 | com.android.htmlviewer | 后备可用版本 |
| 应用B-桌面显示版 | com.android.htmlviewer | 实验组 |

## 如果三个包名全部被拒

说明该车的白名单与手上的样本不是同一套（可能是车型/系统版本差异）。
此时让用户自己取证：
1. 从车机自带应用商店下载一个**不常用**的应用；
2. 用「甲壳虫 ADB 助手」等工具查出它的包名；
3. 卸载该应用；
4. 把包名提供给适配方，复用该包名重打包。

（不要选已预装的系统应用，会签名冲突。）
